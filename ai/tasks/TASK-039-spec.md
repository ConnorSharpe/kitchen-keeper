## Origin

Raised by the user on go-live day (2026-07-22), while looking for a place to do manual pre-launch verification without risking real user data. Investigation (this session, by directly inspecting the live Vercel project, not assumed) found there is currently **no isolated environment at all** — every surface the team could use for "dev testing" today (local dev, every Vercel Preview deployment, and Production) reads and writes the exact same database. This task specs the fix: give Preview deployments (and local dev) their own database, plus a stable, bookmarkable URL for manual testing, so this gap doesn't recur for future feature work after today's launch.

## Design

### 1. One persistent Neon branch for all non-production use

Create a single Neon branch (name: `staging` — deliberately matching the git branch name in Design §3, not `development`; one name across git and database reduces the chance of pointing something at the wrong place later) from the current production branch. This becomes the one shared database for Preview deployments and local dev going forward — not a new branch per PR/deployment. A single static branch is simpler to reason about and sufficient for this project's actual usage pattern (solo maintainer, no concurrent contributors today); per-deployment ephemeral branching is explicitly deferred (see Out of Scope).

Before creating it by hand: check whether the Neon-Vercel integration already installed on this project (visible in the Vercel dashboard's Integrations tab) supports "connect environment to a specific branch" natively — if so, prefer enabling that over manual env-var surgery, since it keeps the mapping self-documenting inside the integration rather than as a set of Vercel env-var overrides someone has to know to look for later.

### 2. Repoint the Preview environment's entire Postgres variable family

**Requirement (invariant, not a fixed checklist)**: every connection-relevant setting the Neon-Vercel integration produces for the **Preview** environment — which branch, host, and database it resolves to — must point at the `staging` branch, not just `DATABASE_URL`. This is deliberately narrower than "every variable must differ": some values (e.g. `PGUSER`, pool/sslmode settings) may legitimately stay identical across branches if Neon assigns them the same way; what matters is the connection target, not that every string differs. The acceptance test is a diff against the integration's current output, not a fixed list: after this change, `vercel env pull --environment=production` and `vercel env pull --environment=preview`, diffed against each other, should show every connection-target variable (host/database/branch-identifying values) pointed at different branches, while incidental settings and non-Postgres variables remain whatever D-6 decides. Don't hardcode today's variable names as the requirement itself — the integration owns that set and can add/rename variables over time, which would silently make a fixed checklist wrong without anyone noticing.

As of this session, that set is (illustrative evidence, not the contract): `DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `POSTGRES_URL`, `POSTGRES_URL_NON_POOLING`, `POSTGRES_PRISMA_URL`, `POSTGRES_URL_NO_SSL`, `PGHOST`, `PGHOST_UNPOOLED`, `PGUSER`, `PGPASSWORD`, `PGDATABASE`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DATABASE`, `POSTGRES_HOST` (`vercel env ls`, this session). Missing even one (e.g. code that reads `POSTGRES_URL_NON_POOLING` directly instead of the app's normal `DATABASE_URL`) would silently leave a code path pointed at production — which is why the verification step is a diff against whatever the integration currently produces, not a check against this specific list.

Prefer doing this via the Neon-Vercel integration's own environment-to-branch mapping if it supports that (check the Integrations tab before touching env vars by hand) — that keeps the mapping self-documenting and automatically correct if the integration's variable set changes later. Only fall back to manual `vercel env` edits per-variable if the integration doesn't support it.

This single environment-level change is what makes the fix general: it isolates *every* Preview deployment automatically — the one-off historical Preview deployment, the `staging` branch (below), and any ad-hoc PR/branch preview — not just one specific URL.

### 3. `staging` becomes the default push target; `main` becomes the release-only branch

This reverses today's workflow, per the user's explicit request this round — currently the local checkout is on `main`, tracking `origin/main` (confirmed: `git branch --show-current` → `main`, `git rev-parse --abbrev-ref @{u}` → `origin/main`), so every ordinary `git push` deploys straight to Production. Going forward:

- Create `staging` off `main` and make it the day-to-day working branch — `git checkout -b staging`, `git push -u origin staging`, so future commits/pushes land there by default instead of `main`.
- `main` becomes release-only: promoted by merging `staging` → `main` (fast-forward preferred) only when ready to actually ship to Production. That merge-and-push is the one deliberate action that triggers a Production deploy — not any push made during normal work.
- **No manual aliasing needed** — Vercel already auto-generates a stable per-branch URL, and this project has direct proof of it: `kitchen-keeper-git-main-connorsharpes-projects.vercel.app` (visible in this session's `vercel alias ls` output, Current State above) has been a stable alias for 86 days across dozens of separate `main` deployments, with no manual `vercel alias set` ever run for it. The same mechanism will produce `kitchen-keeper-git-staging-connorsharpes-projects.vercel.app` automatically the first time `staging` is pushed and deployed. Implementation just needs to confirm this URL appears and stays stable across a second push (Verification Steps) — not build alias management that already exists.
- **Vercel's "Production Branch" project setting must stay `main`.** This setting (Project Settings → Git) is what actually decides Production vs. Preview per branch — not GitHub's default branch, and not which branch a developer happens to work on. It was not directly visible via `vercel project inspect`'s CLI output this session (truncated to framework settings) — confirming the current value in the dashboard, and confirming it's untouched by this task, is a verification step, not an assumption.

**What this does *not* need to change, and why:**

- **GitHub's default branch** (currently `main`, confirmed via `gh repo view --json defaultBranchRef`) doesn't need to move to `staging`. It controls where new clones/PRs default to, not what deploys where — that's entirely Vercel's Production Branch setting above. Recommend leaving it as `main` (D-5) so `main` keeps its normal meaning as "the released state of the app" for anyone (including future-you) landing on the repo.
- **GitHub branch protection on `main`** (to make accidental direct pushes to `main` impossible, not just discouraged) — checked this session and it's **not available**: `gh api repos/.../branches/main/protection` returned 403, because this repo is private and branch-protection rules require a GitHub Pro plan (or a public repo). So there is no GitHub-enforced guardrail here — see Known Risks.

### 4. Local dev alignment

Update `server/.env.local`'s Postgres variable family to the same `staging` Neon branch, so local `npm run dev` also stops touching production data. (Confirmed above it's currently on the production host.)

### 5. Canonical migration order

The `staging` branch is a point-in-time fork of production — it will not automatically pick up future Drizzle migrations applied to production. Rather than "remember to sync it," this task defines one required order for every future schema change, so nobody has to invent a sequence later:

1. Apply the new migration to the `staging` Neon branch first.
2. Push/test the corresponding code on the `staging` git branch against it (Design §3) — this is what actually exercises the new schema before it's live.
3. Once verified, apply the same migration to production.
4. Merge `staging` → `main`, which deploys the verified code to Production against the now-migrated production database.

This ordering is the deliverable of this task (documented in `ai/handoffs/` conventions); the actual running of each migration step is still manual (see Out of Scope for why automation isn't built here) — but there is now exactly one correct order to follow, not an ambiguous "keep them in sync somehow."

Between step 3 (production migrated) and the deployment in step 4 completing, production briefly runs the *previous* application version against the *new* schema. Future migrations should prefer an expand/contract pattern where practical (add-then-backfill-then-remove, across separate migrations, rather than a single destructive `drop`/`rename` column) so that brief window doesn't break the still-running old code. Not a concern for this task itself (no schema change), but a standing note for whichever migration comes next.

## Constraints

- No changes to Production's environment variables, aliases, or deployment behavior — this task only touches Preview-scoped configuration and adds one new branch.
- No per-PR/per-deployment ephemeral database branching in this task (see Out of Scope) — one static `staging` branch only.
- Must not require ongoing manual steps beyond the documented migration-order (Design §5) — the whole point is that future Preview/staging testing "just works" without someone re-deriving this setup.
- Ownership of ongoing upkeep (staging DB refresh, migration order, Clerk environment choice) is the user — this is a solo-maintainer project with no other contributors today, so explicit role assignment beyond that would be premature; revisit if that changes.

## Out of Scope (considered, explicitly declined for this task)

- **Fully automatic branch-per-preview-deployment** (Neon's native "ephemeral branch per Vercel Preview" flow, which auto-creates and auto-deletes a fresh Neon branch for every single deployment) — the more sophisticated version of this problem, appropriate for a team with concurrent PRs. Deferred: this project has one maintainer and no concurrent-testing conflicts today. Revisit if that changes.
- **Automated schema-migration sync** between production and the `staging` branch — documented as a manual step (Design §5), not built as CI automation, given this task's scope and timeline.
- **A separate Clerk Development instance** — not built by default; contingent on D-1's answer.
- **Data scrubbing/anonymization pipeline** for the `staging` branch — contingent on D-3's answer; not built unless that decision calls for it.

## Known Risks

- **Shared single `staging` branch means concurrent test sessions could clobber each other's data** — acceptable today (solo maintainer), would need revisiting if this project ever gets concurrent contributors or automated CI test runs against staging.
- **Schema drift if the migration order (Design §5) isn't followed** — a staging test could pass or fail misleadingly against a stale schema. No automated guardrail in this task's scope; relies on discipline until/unless automation is later added.
- **Data (not just schema) goes stale on `staging` over time** — it's a point-in-time fork (D-3); as production data changes, staging's snapshot increasingly diverges, which can make some manual tests less representative (e.g. testing against old pantry contents). Not fixed by this task — revisit with a periodic refresh (re-fork from production) if it becomes a practical problem. **Any such refresh should be treated as destructive to whatever data exists on `staging` at that time** — it replaces the branch's contents wholesale rather than merging, so anything test-specific added to staging since the last refresh is lost. Worth stating explicitly now so a future refresh isn't a surprise.
- **Rollback if Preview is ever mis-pointed back at production (or anywhere else) by mistake**: reverting is cheap — Vercel retains each environment variable's value, so restoring Preview's Postgres family to Production's current values is a normal `vercel env` edit, not a rebuild. If a migration has already been applied to `staging` and something about the branch itself is wrong (not just an env-var mistake), the fix is re-forking `staging` fresh from current production rather than hand-reversing schema changes — the branch is meant to be disposable and cheaply re-creatable, not precious. Worth a one-line runbook note in `ai/handoffs/` once implemented, not a build item.
- **Shared third-party API keys (D-6)**: if `OPENAI_API_KEY`/`GROQ_API_KEY`/`SPOONACULAR_API_KEY` remain shared with Production (default today), staging usage consumes the same quota/billing as real usage — low-severity but worth knowing before doing heavy manual AI-feature testing on staging.
- **If D-1 resolves to "keep sharing the live Clerk instance,"** test accounts created during staging testing will appear in the real production Clerk user list permanently (Clerk doesn't distinguish "test" users within a single Production instance the way Stripe test-mode does).
- **No GitHub-enforced guardrail against an accidental direct push to `main`.** Branch protection is unavailable on this repo today (private repo, free GitHub plan — confirmed via API, returns 403 requiring GitHub Pro or a public repo). Once `staging` is the normal working branch, a stray `git push origin main` (e.g. from muscle memory, or a script/alias that still hardcodes `main`) would still deploy straight to Production with no GitHub-side check. Mitigation is workflow discipline only (confirm `git branch --show-current` before pushing) unless the user later upgrades to GitHub Pro or makes the repo public, either of which would enable a "require PR, no direct pushes" rule on `main`.

## Verification Steps

1. After the Preview env vars are repointed, deploy to a Preview URL and confirm via a direct query (e.g. `SELECT current_database()`, or a `staging`-branch-only marker row) that it's actually running against the `staging` branch — not just by comparing logged hostnames, which pooled connections can make misleading.
2. Create a test record (e.g. a pantry item) via the Preview/staging deployment; confirm it does **not** appear in the production app at `kitchenkeeper.kitchen`.
3. Confirm production reads/writes are completely unaffected by anything done on staging throughout this testing.
4. Confirm local `npm run dev` now also resolves to the `staging` branch, not production (same query-based check as step 1, not just a logged host).
5. Confirm `kitchen-keeper-git-staging-connorsharpes-projects.vercel.app` (or whatever Vercel's auto-generated branch URL turns out to be) appears after the first push to `staging` with no manual alias step, and that a second push to `staging` keeps resolving at the same URL.
6. Confirm the daily cron (`/api/push/cron`) does not fire against the staging/Preview deployment (Production-only, per Vercel's default cron behavior).
7. Diff `vercel env pull --environment=production` against `--environment=preview` and confirm every connection-target variable (host/database/branch-identifying values) resolves to `staging` (per Design §2's invariant) — not a check against today's specific 15-name list, which may be stale by the time this runs, and not a requirement that every value differ (e.g. `PGUSER` may legitimately match).
8. Confirm the local checkout's tracking branch is `staging` (`git rev-parse --abbrev-ref @{u}` → `origin/staging`) after this task, so ordinary `git push` no longer targets `main` by default.
9. Push a trivial commit to `staging` and confirm it deploys to Preview (isolated DB), not Production — confirms Vercel's Production Branch setting wasn't accidentally left pointed at `staging`.
10. Merge `staging` → `main` and confirm *that* push is what triggers the Production deploy — confirms the promotion path still works end-to-end.
