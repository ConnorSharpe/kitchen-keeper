## Goal

Let a pantry item's quantity be split across two storage locations after the fact (e.g. "5 of these 6 pouches went to the freezer, 1 stayed in the fridge"), each portion getting its own correct, independently-computed expiry.

---

## Decision: Split Creates a Second Row, or Converts In-Place if Splitting the Full Quantity

If the requested split quantity is less than the current quantity, create a new pantry row representing the split-off portion and reduce the original row by the same amount. If the requested split quantity equals the current quantity, treat the operation as a storage-location change on the existing row rather than creating a second row — splitting 100% of a quantity isn't really a split, and a stray zero-quantity row serves no purpose.

**The original row's ID always represents the remainder; the newly-created row always represents the requested split-off quantity** — regardless of which direction the split goes (e.g. splitting 5 of 6 units to the freezer while the original stays in the fridge behaves identically, ID-wise, to splitting 1 of 6 to the fridge while the original stays in the freezer). This matters because IDs are referenced elsewhere (selections, future links) — the rule must not be "whichever row ends up in a particular storage location," it's strictly "original ID = remainder, new ID = split portion."

The new row's expiry is computed via `computeExpiryForStorage({ name, category, storageLocation, purchaseDate: existing.purchaseDate, existingExpiry: null, source: 'ai_estimate' })`, anchored to the **original row's `purchaseDate`** (not today, same anchor rule as TASK-031 Decision 4) — `existingExpiry: null` so the FoodKeeper lookup always gets a chance to produce a fresh value for the new location rather than inheriting the original row's now-irrelevant expiry.

**System-generated columns are not cloned.** "Clone every field except quantity/storageLocation/expiryDate" (Decision below) refers to business data — `id`, `createdAt`, and `updatedAt` are regenerated normally by the insert itself and are never copied from the original row.

## Decision: Race-Safe via an Atomic Conditional Update, Not `SELECT ... FOR UPDATE`

Two simultaneous split requests against the same row (e.g. two devices, or a double-tap) must never be able to produce a negative or double-counted quantity. The textbook fix — `SELECT ... FOR UPDATE` to lock the row before validating — **is not available on this project's database driver**: `server/db/client.js` uses `drizzle-orm/neon-http`, which (confirmed against Neon's and Drizzle's documentation) only supports non-interactive batched transactions, not the session-held interactive transactions `FOR UPDATE` requires. That capability exists only via Neon's separate WebSocket driver, which this codebase doesn't use anywhere — adopting it here would be an infrastructure change well beyond this task's scope.

**Instead: the quantity decrement is a single atomic conditional `UPDATE`, not a read-then-write.**

```sql
UPDATE pantry_items
SET quantity = quantity - $splitQuantity, updated_at = ...
WHERE id = $id AND household_id = $householdId AND quantity >= $splitQuantity
RETURNING *;
```

Postgres executes the check (`quantity >= $splitQuantity`) and the write as one indivisible operation on that row — there is no window between reading the old quantity and writing the new one for a second concurrent request to land in, because the check *is* the write's own `WHERE` clause, not a separate preceding read. If the `UPDATE` returns no row, either the item wasn't found/owned, or the quantity was already insufficient at the moment this statement ran (a genuine race loser, or simply bad input) — both cases return the same 400/404 outcome to the caller (see API section). This achieves the same race-safety guarantee as row locking, using only what this driver's non-interactive-batch transaction model already supports — the same model `shoppingService.buildFromRecipes()` already relies on successfully.

If the returned (post-decrement) quantity is exactly `0`, this was a full-quantity split — convert the row in place (update `storageLocation`/`expiryDate` on the same row, no insert) rather than proceeding to create a new row. Otherwise, insert the new split-off row (cloned per the Decision above) within the same transaction.

## Decision: Clone Every Field Except Quantity, Storage Location, and Expiry

Per architect review round 1: the original draft specified copying "same name/category/purchaseDate/notes" — an enumerated list that becomes stale the moment a new column is added to `pantryItems` and someone forgets to update this task's description. The rule instead: **the new row is a full copy of the original row, with exactly three fields overridden** — `quantity` (the split-off amount), `storageLocation` (the new location), and `expiryDate` (recomputed). Every other column (name, category, purchaseDate, notes, and anything added to the schema later) is copied as-is, by construction (spread the original row, override three keys), not by a maintained list.

## Decision: No `purchaseGroupId` / Origin-Linking Column, For Now

Raised by architect review round 1 as a reasonable future direction — if analytics, receipt history, or nutrition tracking eventually need to know that two rows originated from the same purchase, a `purchaseGroupId` (or `originItemId`) would let them be linked. Accepted as a fair idea, explicitly deferred: there is no current consumer of that linkage anywhere in this app, and adding the column now would be speculative schema for a feature that doesn't exist yet. Trivial to add later if a real need appears.

## Constraints

1. **Split is atomic via a conditional `UPDATE`, not a read-then-write** — see Decision above. The decrement's `WHERE quantity >= splitQuantity` guard is the race-safety mechanism; the insert (or in-place conversion) happens in the same `db.transaction`, matching `buildFromRecipes()`'s existing precedent, so a failure never leaves quantity double-counted or lost.
2. **Clone-by-exclusion, not enumeration** — every field is copied except `quantity`, `storageLocation`, `expiryDate` (business fields, explicitly overridden) and `id`/`createdAt`/`updatedAt` (system-generated, never copied — see Decision above).
3. **Expiry anchor is the original row's `purchaseDate`**, not today — same rule as TASK-031 Decision 4, applied consistently.
4. **Ownership is enforced as part of the same atomic `UPDATE`'s `WHERE` clause** (`household_id = $householdId`), not a separate preceding ownership lookup — a mismatched household simply fails the same conditional update and returns the same not-found outcome, with no separate round trip needed.
5. **`splitQuantity` must be an explicitly finite positive number** — `z.number().finite().positive()`, not just `.positive()` alone (which does not reject `Infinity`) — rejecting `NaN`, `Infinity`, and non-numeric input explicitly rather than relying on implicit JS coercion.
6. **Fractional quantity precision is an accepted limitation, not a validation rule.** A split producing an oddly precise quantity (e.g. splitting 12 eggs unevenly) is allowed — there's no per-unit precision metadata in this schema (a "dozen" of eggs and a "lb" of chicken have no shared notion of a sensible step size), so no arbitrary rounding rule is being invented here. Documented as a known limitation, not silently ignored.
7. **No audit/history trail is introduced by this task** — the original row's prior quantity is simply overwritten (via the `UPDATE`), not preserved anywhere. If a future activity log or audit-history feature exists, it will not have visibility into pre-split quantities from this task alone. Documented as intentional, not an oversight.

## API Addition

```ts
POST /api/pantry/:id/split
Body: { splitQuantity: number, storageLocation: 'pantry'|'refrigerator'|'freezer' }
// splitQuantity: z.number().finite().positive() — rejects NaN/Infinity/non-numeric explicitly
→ { original: PantryItem, created: PantryItem | null }  // created is null when splitQuantity === full quantity (in-place conversion)
```

**Error responses**: the atomic `UPDATE`'s `WHERE` clause can't itself distinguish "item doesn't exist / isn't owned by this household" from "item exists but quantity is insufficient" — both simply affect zero rows. When the conditional update affects zero rows, a cheap follow-up existence check (`SELECT` by `id`+`householdId` only, no quantity condition) determines which error to return: 404 if the item truly doesn't exist or belongs to another household, 400 if it exists but `splitQuantity` exceeds the current quantity. This follow-up read is purely for error-message quality — it plays no role in the race-safety guarantee, which is already fully established by the atomic update itself.

## Acceptance Criteria

- [ ] A 6-pouch chicken breast item split into 1 (fridge) + 5 (freezer) produces two rows with independently correct expiries (fridge row ~2 days, freezer row ~270 days out from the original purchase date)
- [ ] The **original row's ID** is the one with the remaining quantity in both directions of a split (verify explicitly by splitting a small amount off vs. splitting most of the quantity off, confirming the original ID always stays with the remainder either way)
- [ ] Split with `splitQuantity` equal to the full quantity converts the existing row in place (no orphan/duplicate row created)
- [ ] Split with an invalid quantity (0, negative, `NaN`, `Infinity`, or greater than available) returns 400 with no mutation
- [ ] All non-overridden business fields (name, category, notes, purchase date) remain identical between the original and new row after a split — a behavioral check on the actual saved data, not an implementation detail
- [ ] The new row's `id`, `createdAt`, and `updatedAt` are freshly generated, not copied from the original
- [ ] Splitting an item belonging to another household's pantry returns 404
- [ ] Splitting more than the current quantity on an item that does exist and is owned returns 400, distinct from the 404 case above
- [ ] **Concurrency**: two split requests fired against the same row in quick succession, where their combined `splitQuantity` exceeds the available quantity, never produce a negative quantity or a total split amount greater than what existed — at most one succeeds if only one could validly fit (verify by simulating near-simultaneous requests, e.g. two parallel `fetch` calls in a quick test script)
- [ ] Original row's quantity is correctly reduced by the split-off amount
- [ ] Pantry table visibly distinguishes the two resulting rows by storage location (relies on TASK-031's Constraint 8 badge)

Verification is manual smoke testing against local dev — no automated test suite exists in this repo.
